1. The situation

Sprint 70 contained 11 tickets under epic ABE-5148, all against the DataProcesser (the Batch job that imports client customer files into the Benefit database). Two kinds of work, one per client:

  • Program mapping by ProgramNumber — stop resolving a client's program by ProgramCode / Programs.ClientId / ClientCode (which differ between UAT and PROD) and resolve by Programs.ProgramNumber instead. Four clients already had the Handback report: TRI, TTR, MSU, TMI.
  • Data Processor Report (Handback) + ProgramNumber — retrofit the per-row Inserted / Updated / SameData / Invalid / DuplicateUUID report that ABF shows, onto seven legacy processors that never had it: AEO, CHU, KTC, MSH, KUC, SMC, KPI.

Eleven clients, seven of them legacy code written by different people over several years, each with its own file format (Excel, fixed-width text, PGP-encrypted, zip with member files, email attachment). Done by hand this is a sprint's worth of work for one developer.

6. What the agent did that a script could not

  • Found its own reference implementations. Instead of inventing a report format, it searched git history for the last clients that got the report (TYT, HOT, AOI/MIT) and diffed those commits. The seven retrofits follow the same shape as the existing ones, which is what the reviewer expects.
  • Wrote the shared code first. Two helpers (ProgramTierLookup, HandbackRowCollector) instead of eleven copies. The cap for large files was added to the collector when KTC needed it, then reused for SMC.
  • Refused to invent behaviour. On finding CHU had no program assignment, it queried PROD to see whether that was true for imported customers generally before deciding what "map by ProgramNumber" should mean — and then flagged the decision instead of burying it.
  • Verified the whole set at the end, not just each piece. The shared-ProgramNumber collision only shows up when you simulate every lookup together against real data. That is the query that turned a latent prod bug into a 12th commit.
  • Kept secrets out of the transcript. Connection strings came from Secrets Manager into an in-memory helper; passwords were never printed or written to disk.
  • Left the decisions to the humans. Nothing pushed, no PR, no Jira transition. The summary ends with the behaviour changes that need a BA answer.

8. What the developer still has to do

  • Read the summary and the diff for the two behaviour changes (CHU program assignment, AEON failure handling) and put the CHU question to the BA — via twg jira workitem comment create or the browser (the MCP cannot write to Jira on our tenant).
  • Watch the UAT runs the agent is setting up now; confirm the Handback report renders in ABF for each of the seven new clients.
  • Push, open the PR(s) to the UAT branch, run the AI review in a fresh session (Part 5 §3), then the human review.
  • Keep the untracked local data files and issues/ content out of the repo — the 28 Aug release had to strip exactly that kind of file.

9. If you want to try the same thing

  1. Pick a sprint (or a label) where the tickets are the same kind of change across several clients/modules. Homogeneous batches are where the agent's speed compounds.
  2. Write one prompt with: the scope (JQL-able), the categories of change in your words, and the process rules (commit granularity, branch, what not to touch).
  3. Make sure tunnels, AWS SSO and MCP auth are live before you start — the agent will stop at the first 401.
  4. Read the summary, not the transcript. Then read the diff of anything the summary calls a behaviour change.
  5. When it is done, ask the agent to save what it learned to the project memory. That is what made this session 48 minutes instead of a day.
