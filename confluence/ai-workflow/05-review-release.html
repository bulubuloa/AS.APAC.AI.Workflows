Part 5 of AI in the Development Workflow. Last updated 21 Sep 2026.

Goal of this page: the verified branch becomes a reviewable PR, the PR becomes a documented release, and the release leaves behind the evidence an auditor or the next developer will ask for — what shipped, what scripts ran in what order, what was checked afterwards, and how to roll it back. The agent drafts every artefact; a human approves each gate.

3. AI-assisted code review

Before the human reviewer opens the PR, the agent reviews it — in a fresh session, without the context of having written it, so it reads the diff the way a stranger would. Claude Code's /code-review does this against the current branch or a PR; /security-review runs the OWASP-style pass on the pending changes.

What we ask it to look for, in order:

  1. Correctness — null paths, off-by-one in date ranges, SQL that ignores isDelete/active, EF queries that will N+1, exceptions swallowed in sync loops.
  2. Missed touchpoints — the blast-radius table from Part 3 is the checklist: every 🔴/🟠 row must be either changed or explicitly left alone in the PR body.
  3. Convention drift — new patterns where an existing helper exists; comments that explain what; magic strings that belong in the CMS or config.
  4. Security — input reaching SQL or file paths, secrets in config, new endpoints without the existing auth attribute, PII in logs.
  5. Migration safety — script idempotency, run order, prod-only vs preprod-only headers, the @EffectiveDate-style parameter drift that bit the announcement SPs.

Findings are posted as PR comments by the developer after reading them, not by the agent directly. A finding the developer disagrees with is answered in the PR thread, so the reasoning is on record.

The AI review does not replace the human one. It removes the mechanical findings so the reviewer's time goes to design and business logic. A PR that arrives with zero AI findings and zero human findings is a signal to look harder, not to merge faster.

4. Release documentation

For each production release the agent drafts a page under RSA Releases (or the equivalent for Benefit) from the task files of every ticket in the train. Structure, taken from the 28 Aug 2026 page:

  1. Header — release date, branch → target per repo, tag, Jira fix version, ship-together rules.
  2. Features — one paragraph per ticket, written for the BA, not the developer; links to the PRs.
  3. Steps that need no source deploy — CMS content types/items to publish, DB scripts that are additive and can run ahead, Parameter Store keys, data repairs. Each with env, order and "done ✔ / pending".
  4. Deploy order — numbered, cross-repo, with the tag command.
  5. Post-deploy verification — concrete checks, each with what "pass" looks like.
  6. Rollback — previous tag, scripts that are reversible vs not, snapshot name and PITR window.

The Confluence release note for the Benefit system (e.g. Release Note v21.01) is drafted from the same source with the developer sections stripped. Both are published through the twg CLI (Part 1, §6) after review.

5. Production deploy and evidence

The RSA backend deploys through CodePipeline on a prod/YYYYMMDD_NN tag with a mandatory manual approval; the mechanics, downtime window and rollback evidence are on . The agent's role during the deploy:

  • Before: confirm every "no source deploy" step is ticked; confirm the RDS snapshot exists (aws rds describe-db-snapshots); confirm the prod Web.config/Parameter Store keys the release needs are present.
  • During: watch the pipeline (aws codepipeline get-pipeline-state) and the log group; report stage transitions as one-line status updates.
  • After: run the post-deploy checks from the release page, with Playwright where they are UI checks and SQL where they are data checks; write results and timestamps into the release page; add the Jira comment that closes the loop for the BA (addCommentToJiraIssue, after you read it).

The agent never clicks Approve, never pushes the tag on its own, and never runs a prod script. It prepares the command and the human runs it.

6. Closing the ticket

  • Jira: comment with the release tag, the verification result and any follow-up ticket (e.g. the back-fill). Transition is done by the developer or QA per the project's workflow.
  • Task file: ## Release section filled; the file is now the historical record and can be archived.
  • Memory: anything non-obvious learned during the ticket (an environment quirk, a CMS gotcha, a script that must not be re-run) goes into the team's shared notes, not into one developer's head.
