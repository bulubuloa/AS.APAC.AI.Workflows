Second worked example for AI in the Development Workflow — a small, ordinary ticket, so the shape of each step is easy to see. Session of 21 Sep 2026, repositories ABCB (apac-benefit-client-backend) and ABF (apac-benefits-frontend), both on develop — the branch that feeds the SIT pipelines (staging = UAT, main = PROD). Last updated 21 Sep 2026.

What this page is. One Critical story, ABE-5461 Payment Report – Display and Search by Job ID, taken from Jira to two committed branches in about twenty minutes with one prompt. Every artefact on this page exists: the task file issues/ABE-5461.md, the commits, the SQL script, the numbers. Compare with the Sprint 70 example for the other end of the scale.

1. The prompt

"please going with other example, the ticket ABE-5461"

Nothing else — no repo names, no hint where the report lives. The agent had the connections from Part 1 and the memory notes from earlier tickets; the rest it had to find.

2. Fetch (Part 2) — 1 minute

getJiraIssue + a JQL fetch for comments, links, attachments, parent and sub-tasks: none of them. A clean ticket with three numbered acceptance sections. The task file issues/ABE-5461.md was written from the template: the story verbatim, a one-line Goal, six Requirements (one tagged inferred), six checkbox acceptance criteria, an inferred Out-of-scope, and two open questions that the analysis then answered:

  • Is "fulfilled through the RSA Platform" a stored attribute, or implied by the job link?

  • Is "Job ID" the RSA job number the popup shows, or an internal id?

3. Analysis (Part 3) — 12 minutes

3.1 Locating the code

Question

Answer, with the file that proves it

Which screen is "Payment Report → Report Details"?

ABF Pages/Reports/Finance/FinanceBreakdownReport.razor (report name FinancePayment) — found by grepping the label "Case Number" the ticket mentions

Where does the data come from?

GET api/clients/report/get-detailed-payment-report → ReportService.GetDetailedFinanceReport → MySQL stored procedure Benefit_SP_GenerateDetailedFinanceReport; Excel/CSV/Text use the same call

Which repo holds that API?

Same repository as the data processors, but the ClientService.API project only exists on develop — the data-processor branches strip it. A second checkout (Omnicasa.Mobile.ABCB.Clone) on develop is where the change goes

What does the View Redemption popup show as Job ID?

CustomerRedemptionDetail.razor:133 → roadSideResponse.JobId ← customer_redeemed_privileges.RoadSideJobId (CustomerPrivilegeInventoryService.cs:965). One column, so on-screen, Excel and popup agree by construction

What is "Redemption Mode = Fulfillment"?

privileges.IsSpecificBookingRequired — PrivilegeV3Service.cs:185 exposes it as RedemptionModeIsFullfillment

What is "fulfilled through the RSA platform"?

No column. RoadSideJobId is written only by the RSA redemption endpoints (PrivilegeService.cs:4380, :5153, :12019), so a non-null value is the marker

3.2 Verifying against data (read-only, UAT and PROD)

Fact

Value

PROD redemptions carrying a job id

135,701 of 235,993 — all but one on Fulfillment privileges (that one is cancelled)

Job id shape

135,700 are 10 characters (26JB…); one is 4, one is 18; one is lower-case → the filter must be case-insensitive, as the ticket says

Column collation

utf8mb3_general_ci → LIKE already ignores case; no UPPER() needed

Stored procedure, repo vs live

SHOW CREATE PROCEDURE on both environments: the repo file …sp_2.sql equals UAT; PROD differs — inner joins where UAT has LEFT JOIN, and Status NOT IN (4,3,6) where UAT has (4,6)

The last row is the finding that matters. Without the diff, the "obvious" script — take the repo file, add a column — would have silently changed which rows the production report returns. It became a question for the BA and a warning in the script header instead.

3.3 Blast radius

  • 🟠 The Excel column headers come from ImportExportHeader.BreakdownFinance.Header, an ordered list shared with a legacy export in PrivilegeService that is still reachable from ABF. Renumbering orders 7–42 to slot Job ID in at 7 would have shifted that export's columns. Decision: add JobId as order 43 and insert it by position in the new export's mapper — the dictionary's insertion order is what drives the columns.

  • 🟢 Four other reports (Corporate, Unpaid, Unscheduled, Fourth-night) call the same procedure through the one method; the new parameter defaults to NULL for them and the extra column is ignored.

  • 🟢 The popup is untouched.

All of this went into the task file under ## Analysis — understanding, facts table with [measured] tags, design, blast radius, two questions for the BA, plan — before any code changed.

6. What the developer does next

  1. Push both branches and open the PRs to develop (the agent's shell has no Bitbucket credential — its push was refused, which is the right default).

  2. Apply the SP script on the SIT database (command in the task file), let the SIT pipeline deploy the merge, check grid / filter / Excel / popup, attach screenshots to the ticket for QA.

  3. Before staging and main: answer the two BA questions (keep PROD's two SP differences or adopt SIT/UAT's; Excel header JobId vs Job ID) and run the script on each database ahead of the deploy.

  4. AI review of the PRs in a fresh session, then human review.

7. What this small ticket shows

  • Analysis is not overhead, even for a two-file change. The two things a straight implementation would have got wrong — the drifted production procedure and the shared header list — were both found by verifying rather than assuming, in about ten minutes.

  • Read-only can prove most of it. The filter semantics were demonstrated on real UAT data without deploying anything.

  • The task file is the deliverable. By the end it holds the brief, the analysis with citations, the commits, the evidence table and the open questions — the PR description and the Jira comment are copied out of it.

  • Stopping points are explicit. No shared-DB writes, no push without credentials the developer chose to give; the page says exactly what is left.

  • The developer's one question was worth more than the twenty minutes. "PR to develop/SIT first?" corrected a branch-base mistake that would have sent the change to the wrong environment. Process knowledge like this belongs in the docs so the next agent does not need the question.
