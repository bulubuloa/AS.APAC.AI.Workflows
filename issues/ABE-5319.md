## 2. Root cause of the marker bug

`BkkRsa.NearProvider.js` builds the pin path straight from the group name:

```js
iconName = one.provGroupName;                                   // then:
marker.setIcon('/content/marker/standard/' + iconName + '.png');
```

`provGroupName` arrives in **two different spellings**, and only one of them was ever a real file:

| Source | Value | Resolves to | Live status |
|---|---|---|---|
| RSA DB — `ProviderSyncBenefitController.cs:697` writes `request.ProviderGroup` | `Porsche` | `Porsche.png` | **404** |
| CMS overlay — `MswsController_JobOthers.cs:378` writes `cmsItem.Group` | `Porsche RSA` | `Porsche RSA.png` | **404** |
| CMS overlay, Honda | `Honda RSA` | `Honda RSA.png` | **404** |

Confirmed by fetching them from the live SIT server:

```
purple.png       200  image/png   1543 bytes
purple-dot.png   200  image/png   1356 bytes
Porsche RSA.png  404  text/html
Honda RSA.png    404  text/html
```

So Porsche had no pin at all — and Honda is broken too whenever the CMS overlay applies, which
is why the fix maps both known groups rather than special-casing Porsche alone.

**Second defect:** clicking a provider that has no direction yet repaints the marker from
`vinPosGapInSec` only, ignoring the group entirely (`BkkRsa.NearProvider.js`, two sites). A
purple pin reverted to green/orange the moment an agent selected it.

## 3. The change

**`BkkRsa/Scripts/rsa/BkkRsa.NearProvider.js`** — one resolver, used at all four icon sites:

```js
var BKKRSA_GROUP_MARKER = [
    { match: /porsche/i, icon: 'purple' },
    { match: /honda/i, icon: 'honda' }
];

function bkkRsaGroupIconName(provGroupName, suffix) {
    var g = (provGroupName || '').toString().trim();
    for (var i = 0; i < BKKRSA_GROUP_MARKER.length; i++) {
        if (BKKRSA_GROUP_MARKER[i].match.test(g)) return BKKRSA_GROUP_MARKER[i].icon + suffix;
    }
    return g + suffix;   // unmapped groups keep the exact name they used before
}
```

Anything not in the table falls through unchanged, so *"existing provider groups retain their
current marker colors and display behavior"* holds literally — `VIN GROUP` still resolves to
`VIN GROUP.png` exactly as it did.

The click path now carries the group across the direction refresh:

```js
// ABE-5319 the direction response carries no CMS-enriched group, so keep the
// one the marker was drawn with - otherwise the group pin reverts to green/orange.
let grpName = vinMarker.vinModel.provGroupName || one.provGroupName;
$.extend(vinMarker.vinModel, one);
if (grpName) vinMarker.vinModel.provGroupName = grpName;
```

**`BkkRsa.Core/AppCode/Models/NearProviderModel.cs`** — AC4's deleted-provider rule, matching
the guard the Provider Users list already applies:

```csharp
// ABE-5319 deleted providers must never load onto the map, same rule as the Provider Users list
+ "\r\n    AND (ua.isDelete = 0 OR ua.isDelete IS NULL)"
```

## 5. Open items

**AC4 has a data prerequisite, not a code gap.** No Porsche provider can appear on the map yet:
`GetSql_LoadProvider` requires `tokenSerial`, `lat`, `lng`, `active=1`, `istatus=READY` and a
matching `VehService` row, and `pordealer10`'s only truck `v2781` is still **`NOTREGIS`** — the
Truck List confirms it. QA needs to register a Porsche truck through the provider app and let it
report GPS before the purple pin can be seen with genuine data. The specs relabel the response
until then; once the truck exists, drop the relabelling and the same assertions hold.

**AC5 — one label to confirm.** The tooltip is unchanged and already renders Vehicle ID, Vehicle
Name, Vendor ID (`accountId`), phone, licence plate, province, distance to CM, most-recent active
time and current location. **Client Name** is not in the current tooltip. Since AC5 says the
tooltip *"follows the existing provider tooltip behavior and layout"*, I have left it alone —
worth one check against the ticket's screenshot with the BA rather than inventing a field.

**Honda is fixed as a side effect.** `Honda RSA` from the CMS overlay used to 404. This restores
Honda's intended pin rather than changing its colour, but it is a visible change on any
environment where the CMS overlay is live and worth calling out in the release note.
