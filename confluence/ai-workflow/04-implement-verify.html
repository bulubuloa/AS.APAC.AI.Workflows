Part 4 of AI in the Development Workflow. Last updated 21 Sep 2026.

Goal of this page: the plan from Part 3 becomes a diff on a feature branch that builds, passes tests, and is seen working — in a real browser on SIT/UAT and in the database — before anyone is asked to review it. The evidence goes into the task file under ## Implementation and ## Verification.

1. Three ways to run it

The same implementation steps run under three levels of autonomy. Pick by how well the plan is understood and how visible the change is.

Whatever the mode, the agent never merges. Merging and deploying are Part 5 and are human actions.

2. Implementation rules the agent follows

  • Branch first — from the branch that feeds the first test environment, which for ABCB/ABF/ABVB is develop (SIT), not main. The PR goes to develop; QA tests on SIT; promotion to staging and main follows (see table below), named feature/ABE-xxxx-short-slug or, for a release train, release/uat/ABE-xxxx-…. Sub-tasks stack commits on the parent's branch; no second PR.
  • Match the codebase, not the textbook. Existing patterns win: the same controller style, the same SQL helper, the same Kontent client. New abstractions are a question for the reviewer, not a unilateral decision.
  • Additive schema only. New columns nullable or defaulted, widening not narrowing, stored-procedure changes with CREATE OR ALTER. Scripts land in DatabaseScript/<Release>/ with a header stating env, order and rollback. A script that is not idempotent does not ship.
  • Build and test before showing anything. dotnet build / msbuild for the .NET projects, npm run build + lint for the front end, the unit tests for the touched area. A red build is fixed by the agent, not reported.
  • Stage what you changed. git add <files>, never git add -A. Data files, dumps, screenshots and .codex/.claude local config never enter a product repo (the 28 Aug release had to strip exactly that).
  • Commit message = ABE-xxxx Short imperative summary, one line, no body, no AI co-author trailer. One commit per logical change; umbrella tickets get one commit per listed issue so a bad one reverts alone.
  • Comments say why, not what, one line, ticket ID inline (// ABE-5457 Ver2 sync must carry the mobile flag).
  • Secrets never appear in the diff. Config goes to Parameter Store / Secrets Manager; the agent reads them with aws ssm get-parameter and writes only the key name into code.

3. Verification — the part that is not optional

"It compiles" is not evidence. Every change with a visible surface is exercised the way a QA engineer would exercise it, and the agent looks at the result — screenshot, DOM snapshot, query output — rather than assuming.

3.1 Browser (Playwright MCP)

  1. Navigate to the SIT/UAT screen; log in with the shared UAT agent account (never a personal prod account).
  2. Reproduce the before state if the fix is not yet deployed there — that becomes the baseline screenshot.
  3. Deploy the branch to SIT (push) or run the app locally against UAT data.
  4. Drive the exact path in the acceptance criteria: fill, click, wait, browser_snapshot, browser_take_screenshot. Read the network requests when the UI hides an error.
  5. Save screenshots as issues/<KEY>-<step>.png and reference them in the task file.

For regression on RSA, the agent can run the Playwright e2e suite (449 cases across 22 feature sheets) or the subset tagged for the touched area; see . A failing case that pre-dates the change is reported, not "fixed" by editing the test.

3.2 Database

The same read-only queries from the analysis, re-run after the change, with before/after counts side by side. A fix that changes data through a sync or a script must show the row count it touched on UAT and the count it would touch on prod.

3.3 Logs

aws logs filter-log-events on the SIT/UAT log group for the minute the test ran: no new exceptions, the expected info line present. For Lambda-based sync (ABVB), the invocation log for the run that carried the test vendor.

4. When the agent cannot verify

  • Screen behind Azure AD SSO → Chrome extension tools on your logged-in session, or you check that one screen and the agent records what you saw.
  • No SIT for the repo (ABCB) → local run against UAT data with the exact input file; the run log is the evidence.
  • Behaviour only reproducible in prod → do not test in prod. Reproduce the data condition on UAT with a SELECT-driven copy, and state in the PR that prod was not exercised.
  • Cap: ~5 fix–rebuild–screenshot cycles on one issue. After that the agent surfaces the latest screenshot and its diagnosis instead of looping.

5. Guardrails

  • No writes to prod — code, data or config — from this step. Ever.
  • UAT writes only through the application or a reviewed script, never ad-hoc UPDATEs "to make the test pass".
  • A test the agent edits to pass is a finding, not a fix. It goes in the PR body under Decisions.
  • Screenshots and logs from UAT may contain test-customer data; they stay in issues/, not in the repo and not in the PR.
