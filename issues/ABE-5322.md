# ABE-5322 — Incorrect dealer status displayed in RSA

**Type:** Bug · **Priority:** Major · **Epic:** ABE-3384 Production Follow-ups
**Repos:** `Omnicasa.Mobile.ABVB` (sender) + `Omnicasa.Mobile.ABMB` (receiver)

Reported: *NIMITMAI HONDA AUTOMOBILE CO.LTD.*, Vendor ID 11729 — deactivated in Benefit, still
**Active** in RSA.

---

## 1. Answer

**Already fixed in code by ABE-5320. Neither half is in production.** This needs promotion plus a
backfill, not new development.

There are **two independent causes**, and both had to be fixed for deactivation to propagate:

| # | Where | Defect | Fixed by | In prod? |
|---|---|---|---|---|
| 1 | ABVB `SyncDataToRSADealerVer2` | never sent `BActive` at all | `e0e4853` | **No** — in `develop`, not `main` |
| 2 | ABMB dealer sync update branch | ignored `BActive`; only set it on insert | `874892d` | **No** — in `roadside_release_sit` only |

Either one alone leaves the bug intact: with only #1, RSA receives the flag and discards it; with
only #2, RSA is willing to apply a flag that never arrives.

---

## 2. Cause 1 — the Ver2 sender never sent the status

`VendorService` has two dealer-sync paths:

```
SyncDataToRSADealer      (v1,  line 2945)  -> called at 2599 / 4307   BActive present all along
SyncDataToRSADealerVer2  (Ver2, line 3034) -> called at 2830 / 4759   BActive MISSING until ABE-5320
```

The Benefit vendor screens use the **Ver2** endpoints, so the live save path was the one without
the flag. The v1 path having always carried `BActive` is why this looks like a regression that
"used to work" — the behaviour was lost when the flow moved to Ver2, not when the field changed.

ABE-5320 added it:

```csharp
// ABE-5320 without this the RSA dealer never follows the vendor's active state
BActive = vendor.Status == Databases.VendorStatus.STATUS_ACTIVE_CD,
```

## 3. Cause 2 — the receiver ignored it on update

In `ProviderSyncBenefitController`, `bActive` was written **only when the dealer row was created**:

```csharp
clientDealer.bActive = request.BActive ?? true;      // insert branch (line 718) - always existed
```

The update branch never touched it, so a dealer that existed in RSA kept `bActive = 1` forever, no
matter what Benefit sent. ABE-5320 added the missing line:

```csharp
clientDealer.bActive = request.BActive ?? clientDealer.bActive;   // update branch (line 290)
```

## 3a. Reproduced on SIT — with real data

SIT already has both fixes deployed, and the mismatch is still visible there. Cross-checking the
Kontent Delivery API against `cloud.ClientDealer`:


Deactivating in Benefit does **not** unpublish the Kontent item — it stays published with
`vendor_status = inactive`, so anything reading CMS still gets the record back.

Three RSA dealers whose CMS vendor is inactive/archived are still `bActive = 1`:

| dealerId | dealerCode | dealerName | CMS status | RSA |
|---|---|---|---|---|
| 394 | Annie116 | Annie92261 | inactive | **Active** |
| 402 | OT0001 | Sophia 25 - DealerShip | inactive | **Active** |

The dealer list shows all three with a green **Active** badge (`DealerList-Partial.cshtml` renders

Note `archive` is covered by the ABE-5320 mapping: `BActive = vendor.Status == STATUS_ACTIVE_CD`
is false for anything that is not active, archive included.

## 4. Why the symptom looks contradictory

The reporter saw *inactive in Benefit and CMS, Active in RSA*. That is exactly what the code does,
because `DealerController` reads status from two different places:

| Action | Source of `bActive` | Shows |
|---|---|---|
| `List()` (line 45/51/57) | `cloud.ClientDealer.bActive`, **no CMS overlay** | the stale DB value → **Active** |
| `Edit(int id)` (lines 134, 332) | overlaid from CMS (`joModel["bActive"] = cmsDealer.BActive`) | the truth → Inactive |

**Correction to an earlier version of this analysis:** the Edit overlay is not a reliable source of
truth either. `DealerDetailCMS` does not read Kontent directly — it calls a Benefit endpoint
(`{BenefitKontentAi}dealers/{vendorCmsId}`), and the overlay is wrapped in a try/catch that falls
back to the database on any failure:

```csharp
catch (Exception ex) { /* Log error but don't fail - just use database data */ }
```

So if that endpoint is unreachable, unconfigured or returns null, Detail silently shows the same
stale `Active` as the list. Detail is therefore *sometimes* right, which is worse than consistently
wrong — it makes the bug look intermittent.

Once the sync is fixed the DB value is correct and every screen agrees, with no change to
`DealerController` required.

## 5. What to do

1. **Promote ABVB** `e0e4853` from `develop` to `main` (prod).
2. **Promote ABMB** `874892d` from `roadside_release_sit` toward prod. Note ABMB's `develop` and
   `main` do **not** have it either, so the promotion path needs deciding, not just a deploy.
3. **Backfill.** The fix only corrects a dealer when its vendor is next saved in Benefit — nothing
   re-syncs historic rows. Dealer 11729 and any other already-deactivated vendor stay `bActive = 1`
   until touched. Either re-save the affected vendors, or run a one-off reconciliation of
   `cloud.ClientDealer.bActive` against CMS/Benefit status for CMS-linked dealers.

Deployment order does not matter between the two repos — the bug persists until both land, and
neither breaks anything on its own.

## 6. Verification gap — worth closing before promoting

The three stale dealers in §3a were all created on 14 Apr 2026, long before the fix reached SIT on
18 Aug, so they prove the **backfill gap** — not that the fix is broken. Nothing has yet deactivated
a dealer *since* the fix deployed, so the forward path is still confirmed by code trace only.

That is the one open question, and it decides whether any further code is needed. Before promoting
to prod, run the ticket's own reproduction steps on SIT:

1. Deactivate a CMS-linked dealer in Benefit SIT (e.g. one of the `pordealer*` vendors, dealerId
   410–417, clientId 2209).
2. Confirm `cloud.ClientDealer.bActive` flips to 0 for that `vendorCmsId`.
3. Confirm the RSA **dealer list** shows Inactive — that is the screen in the ticket, and the one
   with no CMS overlay to mask a failure.
4. Reactivate and confirm it flips back — the update branch must work in both directions.

Step 3 is the one that matters: checking only the Edit screen would pass even if the sync were
still broken, because that screen overlays CMS.
