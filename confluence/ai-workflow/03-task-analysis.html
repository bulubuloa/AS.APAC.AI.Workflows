Part 3 of AI in the Development Workflow. Last updated 21 Sep 2026.

Goal of this page: before a line of code changes, the task file gains an Analysis section that names the root cause (or the design), cites the exact code, quantifies the blast radius from real data, and lists the questions only a human can answer. The BA gets the same content as a Jira comment.

1. What "analysis" means here

Most AI-assisted bugs go wrong in the same way: the agent reads the ticket, finds the first plausible line of code, and patches it. The patch is often correct for the one example in the ticket and wrong for the other 300 rows nobody looked at. Analysis is the step that forces the agent to verify before it believes — in the code, in the database, in the CMS, in the logs — and to write down what it found in a form a reviewer can check.

The output is text, not code. It is appended to issues/<KEY>.md under ## Analysis and, once you have read it, posted to the ticket.

3. Invoking it

Either the slash command (/task-analyse issues/ABE-5457.md, defined in .claude/commands/task-analyse.md at the workspace root) or a plain prompt. The prompt below is the one that produced the ABE-5457 audit; it is deliberately explicit about verification and about what not to do.

Read issues/ABE-5457.md. Do not change any code. Find the root cause of the provider not appearing in Auto mode: trace the autocomplete request from the RSA web app to the SQL it runs, then trace how that provider's row is populated by the Benefit → RSA sync (ABVB VendorServerless and the RSA ProviderSyncBenefit controller). Verify each claim against the prod DB with SELECT-only queries through the existing tunnel, and against the Kontent prod Delivery API. Then audit every other place in BkkIsos47.sln that reads provider fields from cloud.UserAccount, and tell me what breaks if we stop syncing and read from the CMS only. Cite file:line for every code claim and the query + row count for every data claim. Tag numbers [measured] or [assumption]. Append the result under ## Analysis in the task file. List questions for the BA separately.

4. Worked example — ABE-5457 (condensed)

The ticket: one provider missing from Auto-mode dispatch. The analysis, done on 16 Sep 2026 against prod data, read-only:

4.1 Root cause (step 5)

AutofillController.ProviderName (BkkRsa/Api/AutofillController.cs:83) adds ua.isProviderMobile == true to the query when timeStampMode == "A". Both lookup paths — RSA name match (:87) and CMS-name → vendorCmsId (:101) — go through that base query. The live Ver2 sync ProviderSyncBenefitController.ProviderSyncDataVer2 (:494-570) writes dispName, userName, mobile, active, group and note but never isProviderMobile; only the legacy v1 MapUserAccount (:743) does. The Benefit-side request models (VendorServerless.Shared/Requests/ProviderRoadside.cs:27-42) carry no mobile field at all. The provider edit page overlays the CMS value (ABE-5319), so the screen shows Mobile Provider ticked while the column says 0 — which is exactly why the ticket looked like a UI bug.

4.2 Facts the analysis rests on (step 4)

4.3 Blast radius (step 6)

The sweep found 30+ touchpoints across identity/auth, dispatch, job save, monitoring, partner API and reports that read provider fields from the RSA table, each rated 🔴 breaks / 🟠 degrades / 🟢 unaffected under a "CMS-only" design. Three examples:

  • 🔴 Near-provider SQL for Auto dispatch joins cloud.UserAccount inside the query — cannot post-filter on a CMS call per dispatch.
  • 🔴 Benefit redemption validation matches on BenefitVendorId, a synced column — stopping the sync reintroduces the name-matching bug ABE-4868 removed.
  • 🟢 Partner app endpoints key on accountId from the JWT and never read display fields.

Conclusion for the BA: the one-line fix (write isProviderMobile in the Ver2 sync) is safe; the "read everything from CMS" idea floated in the ticket is not, and the table shows why.

4.4 Questions raised, not answered (step 7)

  • Back-fill the 317 providers from the CMS flag now, or let the next sync fix each one as it is edited? (Consequence: 317 providers become eligible for Auto dispatch overnight, including call-centre vendors.)
  • Is mobile_vendor=yes on 687/752 vendors intended? If not, the CMS needs cleaning before any back-fill.

4.5 Plan (step 8)

  1. ABMB: map isProviderMobile in ProviderSyncDataVer2 from the incoming request; ABVB: add the field to ProviderRoadsideVer2 / VendorRequestVer2 sourced from the Kontent module element.
  2. Unit test on the sync mapper; Playwright check on the provider edit page and the Auto-mode autocomplete on UAT.
  3. Optional back-fill script, gated on the BA's answer, run on UAT first with a before/after count.
  4. Release note line + rollback: revert the two mappers; the column is additive.

5. Guardrails

  • Read-only, always. Analysis never writes to a database, never edits code, never transitions a ticket. If the agent proposes an UPDATE "just to test", the answer is no — that is Part 4 on UAT.
  • Prod data only when UAT cannot answer. And then SELECT with aggregates; no row dumps of customer data into the conversation.
  • Every number has a provenance. [measured] means the query is in the file and re-runnable; [assumption] means someone has to confirm it before it is quoted to a client.
  • Cite or delete. A code claim without file:line, or a data claim without a query, is removed before the comment goes to Jira.
  • Two sources for anything surprising. "The sync never writes the flag" was checked in code and confirmed by the 317-row count. One without the other is a hypothesis.
  • Time-box. Analysis of a normal bug should be under an hour of agent time. If it keeps sweeping, narrow the prompt: name the repo, the controller, the table.
  • Sub-agents for sweeps, main agent for judgement. "Find every reader of column X across 11 projects" goes to an Explore agent that returns a table; the main session interprets it. Keeps the context small and the reasoning visible.

7. Prompts that work

SituationPrompt pattern
Bug with a clear symptom"Trace <symptom> from the UI action to the SQL/API it hits. Verify each hop against UAT. Do not fix."
Bug that "only happens in prod""Compare the config and data path for <feature> between UAT and prod: Parameter Store, Web.config, CMS environment id, SP definitions. List every difference."
Feature request touching several repos"Map every touchpoint for <entity> across ABMB, ABVB, ABF, ABCB. For each, say what changes to add <field>. Propose the smallest sequence of PRs that keeps each deploy backward-compatible."
"Is it safe to remove X?""Find all readers of <X> including SQL, SPs, views, reports and scheduled jobs. Rate each 🔴/🟠/🟢. Run counts on UAT for the rows that would be affected."
Vague ticket"List what the ticket does not say that you would need to know to implement it. Put each as a question with a default you would pick and why."
