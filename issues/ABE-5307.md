# ABE-5307 — Client-Specific Mapping for Defect Issues

**Status:** OPEN · **Priority:** Medium · **Type:** Story · **Repo:** `Omnicasa.Mobile.ABMB` (RoadSide / GAN) + Kontent CMS

Analysis only — no code changed. Checked against the repo, the live Kontent Delivery API and the
live SIT database.

---

## 1. Verdict

Small, well-shaped change with an **exact precedent already in the codebase**: Brands are filtered
by client the same way this ticket asks for. AC3 is already done (shipped with ABE-4681, verified
live below). The work is a CMS field, a seed, one endpoint, and one JS cache fix.

**But the ticket has a wrong client code, and it fails silently.** See §2.

## 2. Blocker — `PTH` does not exist; Porsche is `POR`

AC4 says seed the new defects with **Client-Specific = PTH (Porsche client)**. On SIT:

| clientId | clientCode | clientName |
|---|---|---|
| 380 | **HOT** | Honda Automobile (Thailand) Co., Ltd. |
| 338 | MBZ | Mercedes-Benz (Thailand) Ltd. |
| 2209 | **POR** | Porsche RSA |

There is **no client with code `PTH`**. `HOT` in the same AC is correct, which suggests `PTH` is a
typo rather than a new code. `POR` is the code ABE-5320 established and wired into the dealer sync
(`RsaDealerBrand`: `porsche_rsa` → `POR`).

This matters because the failure is invisible: defects seeded with `PTH` match no client, so under
AC2's rule ("Client-Specific contains selected Client") they would simply never appear for Porsche
jobs — no error, just an empty list that looks like a data problem later.

**Confirm `POR` before seeding.** If `PTH` is genuinely intended, a client with that code has to be
created first, and ABE-5320's mapping revisited.

## 5. The change

### 5.1 CMS

Add element `client_specific` (text) to the `defect_issue` content type — same shape as
`owner_clients` on `vehicle_brand`, comma-separated client codes. `BrandCmsService` already has
Management API plumbing (`MgmtAsync`, `KontentManagementApiKey`) for the seed.

> Content types are per-environment. SIT and UAT share env `225b0999-fce9-02b4-c44b-ed6990faeeaa`;
> prod is `994226e6-d1a5-023e-0fc9-21571d884f47`. The element and the seed must be applied to both,
> and to any new environment — this bit us on the ABMB Kontent env switch before.

### 5.2 Service — and one semantic trap

`FetchNamesAsync` requests `&elements=name`, so it must also request the new element.

**Do not copy `GetBrandsForClientAsync` literally.** Brands are *exclusive*:

```csharp
// brands: if the client owns any, show ONLY those; otherwise fall back to all market brands
if (owned.Count > 0) { list = owned; restricted = true; }
else                 { list = all.Where(market == th); restricted = false; }
```

AC2 for defects is a *union*, and there is no fallback:

```
Client-Specific = Blank            -> global, applies to every client
Client-Specific contains the code  -> that client
```

So a Porsche job must see the blank/global defects **plus** the `POR` ones. Copying the brand
rule would hide all global defects the moment one client-specific defect exists — which, after
AC4 sets all 14 existing to `HOT`, means a Porsche job sees Porsche defects only and a client with
no defects of its own sees nothing at all. Worth confirming that last case is intended (see §6).

Match on a trimmed, case-insensitive, comma-split list — a `LIKE '%POR%'`-style contains test would
also match a hypothetical `PORT` or `SPOR`.

### 5.3 Endpoint

`/msu/defects/{clientId}`, mirroring `/msu/brands/{clientId}`, reusing the existing
`ClientCodeOf(clientId)` helper.

### 5.4 JS — the bit that will bite

`defectIssueInst.loadData()` caches with a one-shot boolean:

```js
loadData: function () { if (inst.options.loaded) return null; ... inst.options.loaded = true; }
```

That is fine for a global list and wrong for a per-client one: switching the job's client would keep
the previous client's defects. `brandInst` already shows the right pattern — a `clientId` option
plus a `frmMain.clientId` change handler that clears the chain and reloads. Defect Issue needs the
same, and it is already inside that reset chain (`vfClear(... frmMain.defectIssue)`).

## 6. To confirm

1. **`PTH` vs `POR`** — §2. Blocking for AC4.
2. **A client with no matching defects** — under AC2 as written it sees only the global ones, and
   after AC4 (all 14 existing → `HOT`) there are **no global defects left**. So every client except
   Honda and Porsche would get an *empty* Defect Issue list. Almost certainly not intended: either
   some defects should stay blank/global, or non-Honda clients need their own seed. This is the
   second-biggest risk in the ticket after §2.
3. **"Auto-populate the Defect Issue field"** (AC2) — populate the *list*, or auto-select the value
   when exactly one qualifies? The Brand equivalent deliberately does not auto-fill: *"Always a
   dropdown the user picks from — a single owned brand is not auto-filled."* Suggest matching that.
4. **The Model gate.** Defect Issue is currently disabled until a Model is chosen
   (`vfGate(frmMain.defectIssue, !hasModel)`). AC2 says the list loads when the job is created or
   updated, with no mention of Model. Should Defect Issue become independent of Model?
5. **Free text vs list.** The field is a jQuery autocomplete over a plain text input, so a user can
   type any value and save it — the list is a convenience, not a constraint. If Client-Specific is
   meant to *restrict* what can be stored, that needs validation on save, which is not in the ACs.
6. **Retire the legacy path?** `MsuController_Dropdown.DefectIssue` + `cloud.UC_DefectIssue` are
   orphaned. Leaving dead client-aware defect code beside new client-aware defect code invites
   confusion; suggest deleting it in this ticket.
