# ABE-5305 — Update Consult Field Values on Job Screen and Reports

**Status:** OPEN · **Priority:** Medium · **Type:** Story · **Repo:** `Omnicasa.Mobile.ABMB` (RoadSide / GAN)

Analysis only — no code changed. Every claim below is checked against the repo or live **SIT**.

---

## 1. Verdict in one line

The UI, save path and both report columns already work; the real work is **data**, and there is a
hard blocker: the column is `nvarchar(20)` and the new value `"Breakdown – Technical Defect"` is
**28 characters**. It cannot be stored until the column and the view are widened.

---

## 3. The blocker — `nvarchar(20)`

From `BkkRsa.Core/Db/BkkRsaModel.edmx`, four places:

```xml
<!-- storage model -->
JobInfo     :155  <Property Name="consultType" Type="nvarchar" MaxLength="20" />
VW_JobInfo  :806  <Property Name="consultType" Type="nvarchar" MaxLength="20" />
<!-- conceptual model -->
JobInfo     :2130 <Property Name="consultType" Type="String" MaxLength="20" Unicode="true" />
VW_JobInfo  :2234 <Property Name="consultType" Type="String" MaxLength="20" Unicode="true" />
```

The required value measures:

```
'Breakdown – Technical Defect'  ->  28 chars, separator is EN DASH U+2013 (not a hyphen)
```

Consequences if this is not handled first:

1. **The value cannot be saved.** 28 > 20. EF's conceptual `MaxLength="20"` rejects it before SQL
   is even reached, and the column would truncate anyway.
2. **All three screens truncate, silently.** The job screen, Job Report and Compass Report all read
   `cloud.VW_JobInfo`, not the base table. A non-schemabound view keeps the *old* column metadata
   after an `ALTER TABLE`, so widening the table alone yields `"Breakdown – Technical Def"`
   everywhere until the view is refreshed. This is the same trap as ABE-4681, which needed
   `VW_JobInfo` rebuilt from its own definition.
3. **En dash is safe, but only as `nvarchar` + `N'...'`.** The column is already Unicode, so U+2013
   round-trips — provided every migration and seed statement uses `N'…'` literals. A plain `'…'`
   literal silently becomes `?`.

**Also unverified:** `cloud.VC_ConsultType.consultType`'s own width. If it is also `nvarchar(20)`,
the master row cannot even be inserted. It is not in the edmx and I could not query the live DB
(see §7), so this must be checked before starting.

## 5. Work plan

**1. Widen the column (DB, every environment)**

```sql
ALTER TABLE cloud.JobInfo ALTER COLUMN consultType nvarchar(50) NULL;
-- and VC_ConsultType if it is also 20
EXEC sp_refreshview N'cloud.VW_JobInfo';   -- or rebuild from its definition, ABE-4681 style
```

Confirm afterwards that `VW_JobInfo.consultType` reports the new length, not 20.

**2. Update the EF model** — `MaxLength` 20 → 50 in all four places above. Without this, EF rejects
the value client-side no matter how wide the column is.

**3. Replace the master rows**

```sql
DELETE FROM cloud.VC_ConsultType;
INSERT INTO cloud.VC_ConsultType (consultType) VALUES
  (N'Accident'), (N'Breakdown – Technical Defect'), (N'Others');
```

**4. Migrate existing jobs** — after step 1, never before, or the update truncates:

```sql
UPDATE cloud.JobInfo SET consultType = N'Breakdown – Technical Defect' WHERE consultType = N'Breakdown';
UPDATE cloud.JobInfo SET consultType = N'Others'                      WHERE consultType = N'Usage Advisory';
-- blank / NULL: no change, per AC5
```

**5. Reports** — no functional change; two judgement calls in §6.

Deployment order matters: **DB widen + view refresh → app with the new edmx → master rows →
migration**. Seeding the master list before the column is widened gives users a value they cannot save.

## 6. Decisions needed from the BA

1. **Column header casing.** Both reports emit the property name, so the header is `consultType`;
   the ticket screenshots show `ConsultType`. If exact casing matters it is one line in the Job
   Report's `headerMapping`, but the Compass report writes `p.Name` with no mapping at all and would
   need one added. Worth confirming rather than changing 60 report headers' behaviour on a guess.
2. **Job Report on-screen preview.** The exported CSV has the column; the HTML preview does not.
   ABE-5320 hit exactly this and the preview column had to be added. Confirm whether AC4's
   screenshot is the export or the preview.
3. **Ordering guarantee.** The required order is currently produced by `ORDER BY consultType` only
   because the three values happen to sort that way. If the business ever wants a different order
   (or another value), an explicit sort column on `VC_ConsultType` is needed. Cheap to add now,
   invasive later.
4. **Is `Accident` genuinely new?** SIT has never had it. Confirm prod does not hold values beyond
   `Breakdown` / `Usage Advisory` that AC5's table does not cover (see §7).

## 7. Confirm before implementing (needs DB access)

I could not query the RSA databases in this session — the sandbox blocked it — so these are
unverified and each one changes the migration:

```sql
-- a. actual widths
SELECT c.name, t.name AS type, c.max_length/2 AS chars
FROM sys.columns c JOIN sys.types t ON t.user_type_id = c.user_type_id
WHERE c.object_id IN (OBJECT_ID('cloud.JobInfo'), OBJECT_ID('cloud.VC_ConsultType'))
  AND c.name = 'consultType';

-- b. every value in use, per environment - is the AC5 table complete?
SELECT consultType, COUNT(*) n FROM cloud.JobInfo GROUP BY consultType ORDER BY n DESC;

-- c. anything constraining the column
SELECT * FROM sys.check_constraints  WHERE parent_object_id = OBJECT_ID('cloud.JobInfo');
SELECT * FROM sys.foreign_keys       WHERE parent_object_id = OBJECT_ID('cloud.JobInfo');
```

Query **b** is the important one: if prod holds a value outside `Breakdown` / `Usage Advisory` /
blank, AC5 does not say what to do with it, and those jobs would keep a value the dropdown no
longer offers — invisible on screen but still present in both reports.
