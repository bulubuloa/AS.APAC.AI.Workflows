## 1. Summary

Porsche joins Honda and Mercedes-Benz as a third RSA brand whose dealers are maintained
in the Benefit CMS and mirrored into the Roadside (BkkRsa) `cloud.ClientDealer` table,
so agents can pick a Porsche dealer as the **Client Target** (towing destination) on a job.

The good news: the dealer pipeline is already generic. Almost everything in the ticket
exists and works for Honda/Benz. The work is **(a) unblocking a hard-coded two-brand gate,
(b) creating the Porsche master data, (c) closing three pre-existing correctness gaps that
Porsche makes visible, and (d) two new report columns.**

Estimated: **~4–5 dev days** + data setup, spread over 3 repos. (Up from 3–4: the v1 sync path
is confirmed still live, which adds M8–M10 — see §8.)

Everything below is verified against live systems on **2026-08-18** — all three Benefit
databases (**prod** via tunnel 3382, **SIT** and **UAT** via 3375), RSA prod MSSQL (3383),
RSA UAT `BKKRsaStaging`, both Kontent environments via the Delivery API, SSM Parameter Store,
and a Playwright session driving GAN UAT as `hoang.quach`. §8 lists every check and its
result, §9 what is missing per environment, §10 what must be decided before work starts,
§11 the pre-implementation audit, §12 the repeatable Playwright suite. No fact in this document is assumed.

### AC1 — Porsche Dealer qualification

| Condition | Status | Evidence |
|---|---|---|

| Sub-Category `Auto Dealer` | ✅ **exists, no new row needed** | `MasterCode DEALEARSHIP_INFOMATION, MasterNameEN 'Auto Dealer'`, parent `AUTO` — prod `Id 50125`, UAT and SIT `Id 50267`. | Vendor Group `Porsche RSA` | ❌ **missing in all three environments** | Prod `VENDOR_GROUP` children: `HONDA_RSA` (50179), `BENZ_RSA` (50181). UAT and SIT: "Honda RSA" (50584), "Mercedes Benz RSA" (50585) — both with a **NULL `MasterCode`** (§8 finding A). | `IsDeleted = 0` | ⚠️ partly | `Vendors.Deleted` is the soft-delete flag, but deleting a vendor never removes the dealer from RSA today — see AC2 gap G3. |

The identity rule itself needs **no code change**: `Common.GetVendorTypeFromCategory()`
(ABVB `Helpers/Common.cs:89-105`) already returns `VENDOR_DEALER_RSA` for
`AUTO` + `DEALEARSHIP_INFOMATION`, and both the create and update paths iterate
`GetVendorIdentityTypes()` (`Services/VendorService.cs:7219`, called at `:2849` and `:4701`).

### AC2 — Client Dealer synchronization

The mechanism exists and is brand-agnostic **except for one hard-coded gate**:

```csharp
// ABVB VendorService.cs:3086-3097  (SyncDataToRSADealerVer2)
if      (groupCmsCodename == "honda_rsa")         request.ClientCode = "HOT";
else if (groupCmsCodename == "mercedes_benz_rsa") request.ClientCode = "MBZ";
else    return await Result<DealerRoadside>.SuccessAsync(new DealerRoadside());  // ← silent no-op
```

The `else` branch returns **success with an empty payload**, so a Porsche dealer saves
cleanly in the CMS and simply never reaches RSA — no error, no log. Same shape in the
legacy v1 path keyed on the master-data code instead of the CMS codename
(`VendorService.cs:3024-3033`, `HONDA_RSA` → `HOT`, `BENZ_RSA` → `MBZ`).

Upstream, ABF decides which codename is sent:

```csharp
// ABF src/Client/Pages/Vendors/Ver2/VendorHelpers.cs:217-221
internal static Dictionary<int, string> ClientCmsCodeMapping => new Dictionary<int, string>()
{
    { 157, "honda_rsa" },
    { 146, "mercedes_benz_rsa" },
};
```

`UpdateGroupCmsCodename()` (`:229`) overwrites `GroupCmsCodename` from the vendor's attached
clients, so this dictionary wins over the CMS taxonomy codename set at
`AddVer2.razor:2211` / `EditUpdateVer2.razor:2554,2589`.

**Those keys match exactly one environment.** The same two clients sit at different Benefit
ids everywhere: **prod `38` / `68`**, **UAT `38` / `208`**, **SIT `157` / `146`** — the
`ClientCode` (`HOT` / `MBZ`) and `ClientIdExternal` (380 / 338) are the only stable parts. So
`UpdateGroupCmsCodename` matches both brands on SIT, Honda alone on UAT, and neither in prod;
everywhere it misses, the codename falls through to the CMS taxonomy value, which is correct —
so nothing visibly breaks. Adding `{ <PorscheId>, "porsche_rsa" }` would fix one environment
and change nothing in the others: the dictionary needs per-environment configuration or
deletion, not another hard-coded row (§10 C3). `clients.ClientIdExternal` is the durable
Benefit→RSA client link.

On the RSA side `DealerSyncInfoVer2` (`BkkRsa/Api/ProviderSyncBenefitController.cs:223-287`)
is already generic: upsert on `vendorCmsId`, `clientId` resolved from `clientCode`.
Location updates (`DealerSyncLocationVer2`, `:291`) need no change.

**Gaps this AC exposes:**

- **G1 — orphan dealers when the client code is unknown.** `DealerSyncInfoVer2:233-235`
  does `request.ClientId = foundClientId ?? 0;`. RSA prod `cloud.Client` **has no Porsche row**
  (verified — only `HOT` 380 and `MBZ` 338 carry dealers, 238 and 41 respectively), so every
  Porsche dealer would be inserted with `clientId = 0` and reported as success. They then never
  appear in GAN for any client and can never be selected as a Client Target. Harden to fail loudly.
- **G2 — `bActive` is never updated.** The create branch maps it (`MapClientDealer`, `:655-670`),
  but the update branch (`:252-260`) sets code/name/tel/fax/note/dispInfo only. Flipping a
  vendor to Inactive/Archived in the CMS leaves `ClientDealer.bActive = 1` in RSA. This is
  what AC4's word "**active**" hinges on.
- **G3 — deleting a vendor doesn't delete the dealer.** `DeleteVendorByCmsId` (`VendorService.cs:3627`)
  and `DeleteVendor` (`:3552`) call only `DeleteVendorRSA(vendorObj.CloudAccIdExternal)` —
  the *provider* endpoint. `DeleteRSADealerByVendorCmsId` (`:2953`) exists and is wired into
  the update path (`:4755`, when the dealer sub-category is removed) but not into delete.
  This directly contradicts "Deleted vendors shall not be synchronized to Roadside system".

G1–G3 are pre-existing Honda/Benz bugs. Fixing them changes behaviour for those brands too —
call that out in the ticket before merging.

### AC3 — GAN > Client Dealer

**No code change.** `DealerController.List/Edit` (`BkkRsa/Controllers/DealerController.cs`)
queries `cloud.ClientDealer LEFT JOIN cloud.Client` with no brand logic, and `Edit` already
overlays live CMS values via `BenefitCmsService.DealerDetailCMS` (`:100-125`). The map
popup (`MsuController_ClientDealer.cs`) is likewise generic.

Confirmed live on UAT `/dealer/list`: columns are `No | Id | Client | Code | Dealer Name |
View | Address | Province | Status | Insert`, filters are `dealerId, clientId, dealerName,
province, onlyActive, displayAll`, and the Client dropdown is populated straight from
`cloud.Client` — **169 options, none of them Porsche**. Porsche dealers appear the moment
AC2 lands. Verify only.

### AC4 — Job Detail → Client Target

Also almost entirely built:

- UI: `BkkRsa/Views/Msu/Job.cshtml:532-552` (the ♥ button), dialog at `:1806-1821`,
  save handler at `:5240-5290`. No brand conditionals.
- API: `BkkRsa/Api/MswsController_ClientTarget.cs`. On POST it reads the job's `clientId`,
  looks the code up in `cloud.ClientDealer`, and on a miss throws
  **`$"Dealer code '{clientTargetId}' for clientId '{clientId}' was not found"`** (`:96`) —
  character-for-character the message the ticket asks for. On a hit it writes
  `clientTargetId` + `clientTargetName` back to `cloud.JobInfo` and the UI repaints both
  (`Job.cshtml:5269-5272`), which is the "pre-populate dealer code vs dealer name" behaviour.

Both halves confirmed live on UAT job `26JB048514` (clientId 380). Entering `PORSCHE-XX`
produced the alert verbatim:

> `Dealer code 'PORSCHE-XX' for clientId '380' was not found`

**Gap G4 — the lookup ignores `bActive`, proven live:**

```sql
-- MswsController_ClientTarget.cs:85-88
SELECT clientId, [dealerCode], [dealerName]
FROM cloud.[ClientDealer]
WHERE clientId=@clientId AND dealerCode=@dealerCode      -- no AND bActive=1
```

AC4 says "matches any existing **active** Porsche dealer". On UAT, dealer `10104`
(*PHRANAKORN HONDA AUTOMOBILE CO.,LTD.*, clientId 380) has `bActive = 0`. Submitting it was
**accepted**: the field pre-populated with code and name, and `cloud.JobInfo` persisted
`clientTargetId = 10104`. Screenshot: `.playwright-mcp/abe5320-clienttarget-inactive-dealer.png`.
The job was restored to `NULL` afterwards.

Add `AND bActive=1` — but note it tightens Honda/Benz too, and is only fully meaningful once
G2 is fixed (otherwise `bActive` only ever changes on dealer creation). The other precondition
is that Porsche jobs carry the Porsche `clientId`.

## 7. Risks

- **Silent failure by design.** Both dealer-sync methods currently swallow an unmapped
  vendor group as "success". Until item 4 lands, any Porsche misconfiguration looks like a
  working save. Fix this first — it will save hours of debugging in Phase 1.
- **The v1 delete branch is a live hazard, not just a Porsche problem.** With v1 confirmed
  active and `VendorRequestVer2` never writing `vendors.GroupId`, any CMS-created dealer that
  reaches `PUT api/vendors/{id}` has a NULL group and a dealer code — the exact combination
  that triggers `DeleteDealerFromRSA`. That applies to Honda and Benz today. M10 should ship
  ahead of the Porsche enablement regardless of the rest of this ticket.
- **Shared-blast-radius fixes.** G1–G4 all touch code paths Honda and Benz use in
  production. Keep them in a separate commit from the Porsche enablement so they can be
  reverted independently.
- **Environment drift is already here.** V5 proves it: ABF's `ClientCmsCodeMapping` is keyed
  on Benefit client ids 157/146 that exist in no production row. Adding a Porsche entry to
  that dictionary without fixing the keys ships another line of dead code. The Kontent vendor
  group likewise has to be created in every environment separately.
- **Three repos, three pipelines.** ABVB, ABF and BkkRsa deploy independently. Ship ABMB
  item 8 (the loud client-code failure) *before* the ABVB gate opens, or the first Porsche
  sync can create `clientId = 0` orphans that must be cleaned up by hand.

- **M9 as recommended** (resolve the group from `GroupCmsCodename` inside
  `SyncDataToRSADealer`) → the `masterdatas` row is **not needed at all**; Kontent becomes the
  single source of truth for both paths. M1 and M8 drop out of the plan.
- **M9 as "add `GroupId` to `VendorRequestVer2`"** → the `masterdatas` row is **required** in
  all three environments, and M8 stays.

One independent reason to create it anyway: the **Excel import** matches the group by
`MasterNameEN`, so if Porsche's dealers are bulk-onboarded via import rather than hand-entry,
the row must exist with the name spelled exactly "Porsche RSA". Note the import sets `GroupId`

### A5 — `dealerId` is assigned by hand, and Porsche is a bulk load ⚠️ **new finding**

`cloud.ClientDealer.dealerId` is **not** an identity column (`is_identity = 0`), and
`DealerSyncInfoVer2:240-241` assigns `MAX(dealerId) + 1` in application code before inserting.
Prod is at `MAX = 371` across 279 rows. Honda and Benz were onboarded gradually so this never
bit; **Porsche will be a bulk onboarding**, and two concurrent dealer syncs will compute the
same id and collide on the primary key. Either serialise the initial load or make the insert
race-safe. Same pattern, same risk, in `ClientSyncData:51-52` for `clientId`.

### A6 — Dealer-code uniqueness is global ⚠️ **new finding, needs client input**

`VendorService.cs:2300` validates with
`_context.Vendors.AnyAsync(x => x.CodeEN == vendor.CodeEN)` — no country, client, brand or
category scope. A Porsche dealer code that matches **any** existing vendor's `CodeEN` is
rejected at save with *"This DealerCode 'X' is already taken."* Prod currently holds 233 Honda
and 24 Benz dealer codes (Honda's are numeric like `12101`, `13105`; Benz's are `GS…`).

RSA itself is fine either way — `cloud.ClientDealer` has **zero** dealer codes shared across
clients today, and the Client Target lookup is client-scoped.

**This is the one thing still needed from outside:** Porsche's dealer code list, checked against
`vendors.CodeEN` before implementation. If Porsche uses short numeric codes there is a real
chance of collision with Honda's.

### A10 — the end-to-end test found two more bugs, one of them mine ⚠️

The first real Porsche vendor (`pordealer1`, CMS id `7708ce81-79e3-498d-9606-00640e704781`,
created on SIT 2026-08-18 15:54) synced to RSA — but landed on **`clientId 380` (Honda)**
instead of 2209 (Porsche). The CMS item was correct: its `vendor_group` is the `porsche_rsa`
item. So the gate opened and the brand was lost downstream.

**Cause — `AddVer2.razor` overrides the correct group:**

```csharp
:2201  _vendorRequest.GroupCmsCodename = _templateGeneric.VendorGroup?…Codename;  // "porsche_rsa"
:2205  VendorHelpers.UpdateGroupCmsCodename(_vendorRequest, _clients);            // overwrites it
```

`_clients` is `result.Data.VendorClientOptions` — **every client in the system**, not the ones
selected for this vendor. So `FirstOrDefault(g => clientCodes.Contains(g.Key))` always returns
the first mapped brand that exists anywhere: `HOT → honda_rsa`. Every dealer created through
the Ver2 UI on SIT has always been forced onto Honda.

**This is where the C3 decision mattered.** In prod the old id keys (`157`/`146`) matched
nothing, so the override silently no-opped and the CMS value survived — prod was accidentally
correct. Re-keying on `ClientCode` would have made it match in prod too, forcing **every**
production dealer onto Honda. The re-key was the wrong call; the fix is deletion, which is what
C3 originally recommended. Removed in `ABE-5320 Stop overriding the CMS vendor group from the
client list`.

**G5 — a dealer never moves client.** `DealerSyncInfoVer2`'s update branch sets code, name,
tel, fax, note, dispInfo, vendorCmsId and (now) bActive — but never `clientId`. So correcting a
vendor's brand left the dealer under the original client forever, and the ABF fix alone would
not have repaired `pordealer1`. Fixed in `ABE-5320 Move a dealer to the new client when its
vendor group changes`.

### A11 — two unrelated pre-existing bugs surfaced during testing

Both fire on **every** vendor save and are nothing to do with this ticket, but they block CMS
publishing and should be raised separately:

1. **`vendor_external_id` does not exist in the CMS type.** ABVB sends it when updating a
   variant; `template_generic` in env `225b0999` has 25 elements and none of them is
   `vendor_external_id`. Result:
   *"Error updating and publishing variant: … The content type 'template_generic' does not
   contain any element with the codename 'vendor_external_id'"*. The same missing field breaks
   the `CmsMigration` project's build on `develop` (`VendorCmsUpsertHelper`,
   `VendorVariantBuilder`, `VendorFieldMapper`). Someone added the field in code but never in
   Kontent. Either add the element or revert the code.
2. **Publish uses the wrong Management API call.**
   *"Cannot change the workflow step to Published. If you want to publish a language variant
   via the Management API, use the '/publish' endpoint instead."* — `PublishVariantByLanguageCodename`
   sets the workflow step directly instead of calling `/publish`.

Consequence: newly saved vendors stay **unpublished** (`pordealer2` and `pordealer3` have
workflow step `None`; `pordealer1`, created before the regression, is published). Unpublished
items are invisible to the Delivery API, so RSA's live CMS overlay — provider group, dealer
name/address in GAN — silently falls back to stored values. The dealer sync itself is
unaffected, which is why `pordealer3` still reached RSA correctly.

Timing points at the ABVB deploys between 15:54 and 16:29 (PR #933 `ABE-4722`, PR #934
`fix build error`), not at ABE-5320.

### A12 — provider sync already supports every brand
